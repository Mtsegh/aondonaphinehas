Storytelling Platform

GettyStories is a Medium-style publishing platform for writers and readers, built to turn one-time visits into daily habits with author tools, bookmarks, subscriptions, and an engagement system that keeps people coming back.

01

The Challenge

GettyStories needed a rich text editor so writers could format stories with headings, bold text, links, and inline images, the same way any modern publishing tool works. I wired up Quill for that piece, and it worked well immediately: writers typed, formatted, and their story rendered back exactly as written.

The problem showed up once I looked at what actually got saved. Quill hands back raw HTML, and that HTML was going straight into the database and straight back out to every reader who opened the story. Nothing stood between what a writer typed and what every visitor's browser executed. A story containing a stray image tag with a broken onerror attribute, or a pasted script tag, would run in the browser of anyone who opened it, silently, with no warning to the reader or the writer.

On a platform whose entire pitch is trust and daily return visits, that is not a small bug. It's a way for one bad actor to compromise every reader who clicks a single story.

02

How I Fixed It

I moved the security decision from the editor to the data boundary. Instead of trusting whatever HTML the rich text editor produced, I sanitized story content on the way in, before it ever reached the database, stripping script tags, inline event handlers such as onerror and onclick, and anything outside an explicit allowlist of formatting tags: headings, bold, italics, links, images, and lists.

I sanitized again on the way out, so stories saved before the fix would still render safely. Then I tested it the way an attacker would: pasted script tags, malformed image tags, javascript: links, and encoded payloads, checking that each one rendered as plain, harmless text instead of executing.

sanitizeStory.js 
function sanitizeStoryHtml(rawHtml) {
  return sanitizeHtml(rawHtml, {
    allowedTags: ['h1', 'h2', 'p', 'b', 'i', 'a', 'img', 'ul', 'li'],
    allowedAttributes: { a: ['href'], img: ['src', 'alt'] },
    disallowedTagsMode: 'discard'
  });
}
const safe = sanitizeStoryHtml(story.body);
03

What Changed

  • Every story is sanitized on write and on read, so a future editor change can't reopen the hole on its own
  • Verified against common XSS payloads before shipping the fix
  • Reader trust protected without changing how writers use the editor at all

The lesson was simple: never trust a friendly editor to produce safe output. Sanitize at the data boundary, not at the source.
